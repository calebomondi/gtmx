# Deploying GTMX on Render

Four pieces, all on Render, with Supabase for auth and the database:

| Render service | What | Plan |
|---|---|---|
| `gtmx-api` | FastAPI + the agents (`render.yaml` in this repo) | `1c-2g` (Standard), always on, **1 instance** |
| `gtmx-app` | The customer app (`frontend/`) | Static site (free) |
| `gtmx-waitlist` | The waitlist page (`waitlist/`) | Static site (free) |
| `gtmx-admin` | The admin console (`render.yaml` in the gtmx-admin repo) | Static site (free) |

Everything deploys from `main`, and only after CI passes on it. Promote `dev`
to `main` to release.

**Never scale `gtmx-api` past one instance or onto the free tier.** Agent runs,
competitor monitoring and inbox sync live inside its process. A second copy
would duplicate scheduled work, and a sleeping one stops it. A deploy restarts
the process, and runs in flight then fail with a "restarted" message, so
deploy when nobody is mid-discovery.

---

## 1. Before you start

- [ ] Promote `dev` to `main` (merge the `dev` → `main` PR).
- [ ] Top up the Qwen (DashScope) account, or set `LLM_MODELS` to models that have quota.
- [ ] Supabase: note the project's **region**. Render's services run in **Frankfurt**,
      so an EU region (e.g. eu-central-1) keeps database round-trips short.

## 2. Supabase: the production database

1. Supabase → Project Settings → Database → **Connection string** → **Transaction pooler**.
   Copy it (`postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres`).
   - Use the **transaction** pooler (port **6543**). The session pooler (5432)
     allows only as many clients as its pool size (15 on small plans). A
     deploy runs the old and new API side by side, and together they need
     more, so the new one fails to start with `EMAXCONNSESSION`. The app turns
     off prepared statements, which the transaction pooler can't carry.
   - The direct host is IPv6-only and Render can't reach it.
2. Nothing to create: on every deploy, `alembic upgrade head` runs before the
   new version starts and creates or updates the tables. Local data stays local;
   production starts empty. Users already live in Supabase Auth.

## 3. Render: create the services

1. Render → **New → Blueprint** → connect the GitHub repo `calebomondi/gtmx`, branch `main`.
2. Render reads `render.yaml` and asks for every `sync: false` value:

| Variable | Service | Value |
|---|---|---|
| `DATABASE_URL` | api | The transaction-pooler URL from step 2 |
| `SUPABASE_BASE_URL` | api | Supabase → Project Settings → API → Project URL |
| `SUPABASE_SECRET_KEY` | api | Same page → **secret** (service role) key. Server only |
| `ALLOWED_ORIGINS` | api | `https://gtmx-app.onrender.com,https://gtmx-waitlist.onrender.com,https://gtmx-admin.onrender.com` |
| `FRONTEND_BASE_URL` | api | `https://gtmx-app.onrender.com` |
| `ADMIN_BOOTSTRAP_EMAILS` | api | Your admin email(s), comma-separated |
| `DASHSCOPE_API_KEY`, `DASHSCOPE_BASE_URL` | api | From your local `.env` |
| `OPENAI_API_KEY` | api | The OpenRouter key (the backup model) |
| `LLM_MODELS`, `LLM_CHEAP_MODELS` | api | Comma-separated Qwen models with quota, e.g. `qwen-plus-latest` |
| `EXA_API_KEY`, `BRIGHTDATA_API_KEY` | api | From your local `.env` |
| `COMPOSIO_API_KEY`, `COMPOSIO_AUTH_CONFIGS` | api | From your local `.env` |
| `RESEND_API_KEY` | api | From your local `.env` |
| `WAITLIST_FROM_EMAIL` | api | Leave empty until the sending domain is verified in Resend |
| `VITE_API_ORIGIN` | app, waitlist | `https://gtmx-api.onrender.com` |
| `VITE_SUPABASE_URL` | app | The Supabase Project URL |
| `VITE_SUPABASE_ANON_KEY` | app | Supabase → API → **anon / publishable** key |

`WAITLIST_IP_SALT` is generated by Render. The pool sizes, client-IP header
and log format are already set in `render.yaml`.

3. Click **Apply**. The API's first deploy installs dependencies, runs the
   migrations, and passes the `/health` check when the database and agent
   runtime are up.
4. **Check the URLs Render assigned.** If a name was taken, Render adds a suffix
   (e.g. `gtmx-api-x1y2.onrender.com`). Then fix `VITE_API_ORIGIN`,
   `ALLOWED_ORIGINS` and `FRONTEND_BASE_URL` to the real URLs. The `VITE_*`
   values are baked in at build time, so **Manual Deploy → Clear build cache &
   deploy** the static site afterwards.

## 4. Outside Render

- [ ] **Supabase → Authentication → URL Configuration**: Site URL = the app URL.
      Add redirect URLs `https://gtmx-app.onrender.com/**` and `https://gtmx-admin.onrender.com/**`.
- [ ] **Composio**: the managed auth configs need no change. Connections return to
      `FRONTEND_BASE_URL`. TikTok may need a redirect on a domain you own
      (see `docs/launch-plan.md`).
- [ ] **Resend**: verify the sending domain, then set `WAITLIST_FROM_EMAIL`
      (e.g. `GTMX <hello@gtmx.co>`). Until then, waitlist emails aren't sent.

## 5. The admin console

In the gtmx-admin repo: **New → Blueprint** → `calebomondi/gtmx-admin`, branch `main`.
It asks for `VITE_API_ORIGIN` (the API URL), `VITE_SUPABASE_URL` and
`VITE_SUPABASE_ANON_KEY`. Its URL must be in the API's `ALLOWED_ORIGINS`.

## 6. Check it works

- [ ] `https://gtmx-api.onrender.com/health` returns `{"status":"ok",...}`.
- [ ] Sign in on the app, create a workspace, and let discovery run end to end.
- [ ] Join the waitlist on the waitlist page. The signup appears in the admin console.
- [ ] Sign in to the admin console with an `ADMIN_BOOTSTRAP_EMAILS` account.

## 7. Your own domains (when bought)

1. In each Render service → Settings → **Custom Domains**: `gtmx.co` (waitlist),
   `app.gtmx.co` (app), and optionally `api.gtmx.co` (API) and `admin.gtmx.co`.
   Add the DNS records Render shows.
2. Update `ALLOWED_ORIGINS`, `FRONTEND_BASE_URL` and `VITE_API_ORIGIN`, then
   redeploy the static sites.
3. Update the Supabase Site URL and redirect URLs.

`deploy/nginx.conf` is the alternative for a single VM; Render doesn't use it.
